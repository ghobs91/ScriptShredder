# ScriptShredder

Block **third-party JavaScript** on every site — without turning off all JavaScript.

Most script blockers are all-or-nothing: run every script, or run none of them. ScriptShredder sits in the middle. It uses the Manifest V3 `declarativeNetRequest` API to block only `script` requests that come from a different registrable domain than the page making the request. Each site keeps its own JavaScript, while cross-site scripts are stopped before they reach the page.

## What it does

- Blocks third-party `<script>`, dynamic `import()`, and other network-level script requests by default.
- Keeps first-party scripts, including subdomains such as `cdn.example.com` on `www.example.com`, working.
- Lists the third-party scripts detected on the current page in the popup, with an **Allow** action for a single script on that site.
- Adds a per-site pause list for sites that break, stored locally.
- Keeps a local counter of the most frequently blocked third-party scripts.
- Includes a global on/off switch and a badge count in Chromium-based browsers.
- Runs on Chrome, Firefox, and Safari from one codebase with Manifest V3.
- Has no accounts, analytics, telemetry, or network services.

## Browser support

| Browser | Minimum | Notes |

## Build and test

```bash
npm run build:all      # Chrome, Firefox, and Safari MV3 builds
npm test               # unit tests (domains, rules, page classification, counters)
npm run test:e2e       # Playwright end-to-end test in Chromium
```

The first end-to-end run needs a Playwright browser:

```bash
npx playwright install chromium
```

The e2e server maps `site.test`, `api.site.test`, and `cdn.test` to `127.0.0.1` inside Chromium. It verifies that:

1. A script from `cdn.test` is blocked on `site.test`.
2. A script from `api.site.test` (same registrable domain) still loads.
3. The page collector reports the page's script URLs to the extension.
4. Blocked scripts are counted locally and appear in the settings page.
5. Pausing `site.test` through the settings UI lets its third-party script load and stops its counters.
6. Turning protection off lets every script load.
7. Allowing a single script on `site.test` lets it load, and removing that exception blocks it again.
8. Removing a paused site blocks it again.

## How it works

All behavior is expressed as three declarative rule shapes in [`src/lib/rules.ts`](src/lib/rules.ts):

```json
{
  "id": 1,
  "priority": 1,
  "action": { "type": "block" },
  "condition": {
    "domainType": "thirdParty",
    "resourceTypes": ["script"]
  }
}
```

For every paused site, a higher-priority rule allows the whole top-level frame hierarchy:

```json
{
  "id": 1000,
  "priority": 2,
  "action": { "type": "allowAllRequests" },
  "condition": {
    "urlFilter": "||example.com^",
    "resourceTypes": ["main_frame"]
  }
}
```

For every individual script exception, the highest-priority rule allows one normalized script URL when that site initiates it:

```json
{
  "id": 2000,
  "priority": 3,
  "action": { "type": "allow" },
  "condition": {
    "urlFilter": "|https://cdn.other.test/tracker.js",
    "initiatorDomains": ["example.com"],
    "resourceTypes": ["script"]
  }
}
```

The background service worker rebuilds dynamic rules whenever settings change, after install, and when the background starts. Settings live in `browser.storage.local`; the popup and options page never talk to a server.

A lightweight content script runs on `http`/`https` pages and reports script `src` values (plus `modulepreload` and `preload as=script` links) from the top frame. It does not read page text, form data, cookies, or request bodies. The background compares those URLs against the current settings:

- the popup lists the third-party ones and marks each as blocked or allowed;
- the settings page increments a local counter for each blocked script, once per page load.

“Third-party” follows the browser's definition: the request's registrable domain (eTLD+1) differs from the domain of the frame that initiated it. This means:

- `cdn.example.com` on `www.example.com` is **first-party** and loads.
- `cdn.other.test` on `example.com` is **third-party** and is blocked.
- A third-party **iframe** is not itself blocked, and scripts that iframe loads from its own domain are first-party to that iframe. Only network-level script requests are filtered; inline scripts, `eval`, and JavaScript fetched as data and then executed are outside the reach of a declarative network blocker.
- Domain-based detection is blind to CNAME cloaking and scripts proxied through the site's own domain. A tracker served from `tracker.example.com` looks first-party to the browser.
- Dynamic `import()` and worker scripts are blocked but are not represented as `<script>` elements, so they may not appear in the page list or counters.
- The page list and counters cover the top frame. A third-party script inside a third-party iframe is first-party to that iframe and is not blocked or counted.
- The list and counters are inferred from script URLs plus the current rules. They cannot see the browser's final network outcome, so a script that fails for another reason may still be labeled or counted as blocked.

## Safari packaging

```bash
npm run package:safari
```

This builds `.output/safari-mv3`, runs `safari-web-extension-packager`, and writes an Xcode project to `.output/safari/ScriptShredder/ScriptShredder.xcodeproj`. Then:

1. Open the project in Xcode.
2. Choose your development team under **Signing & Capabilities**.
3. Run the `ScriptShredder` scheme.
4. Enable the extension in **Safari → Settings → Extensions**.

The bundle identifier in `scripts/package-safari.sh` is a placeholder. Change it before publishing; the extension target is generated as `<bundle identifier>.Extension` and must stay prefixed by the app's identifier or Xcode rejects the embedded binary.

### iOS Safari (iPhone / iPad)

```bash
npm run package:safari:ios
# optional: npm run package:safari:ios -- com.yourname.scriptshredder
```

This writes an iOS-only Xcode project to `.output/safari-ios/ScriptShredder/ScriptShredder.xcodeproj` and sets the deployment target to iOS 26. The extension manifest also requires Safari 26, so older iOS versions are not supported without lowering both.

A Safari extension on iOS is delivered inside a containing app. It cannot be loaded unpacked or run from a dev server; the app must be signed and installed. Once installed it runs independently of the Mac.

**Free Apple ID (simplest, expires after 7 days)**

1. On the iPhone, enable **Settings → Privacy & Security → Developer Mode**, then restart and confirm.
2. Connect the iPhone, open the Xcode project, and select your personal team under **Signing & Capabilities** for both `ScriptShredder` and `ScriptShredder Extension`.
3. Choose the iPhone as the destination and press **Run**.
4. Trust the app on the iPhone under **Settings → General → VPN & Device Management**.
5. Open the ScriptShredder app once, then enable it in **Settings → Apps → Safari → Extensions** (or **Settings → Safari → Extensions** on older iOS).
6. Set **Website Access** to **Allow** so the content script and counters can run on every site. With **Ask**, Safari prompts per site and the page list may stay empty until you allow it.
7. You can disconnect the iPhone after the first install. The app stops launching when the free provisioning profile expires after 7 days; run it from Xcode again to renew.

**Paid Apple Developer Program**

- A normal development install is valid for about a year and can still be installed once from Xcode, then used untethered.
- **TestFlight** is the best option for installing or updating without a cable. Create an App Store Connect app record, archive and upload the build, add yourself as an internal tester, then install through the TestFlight app. Internal builds do not need App Review; builds expire after 90 days.
- **Ad Hoc** distribution (register the iPhone UDID, export an Ad Hoc IPA, install with Apple Configurator or an OTA manifest) is valid for about a year and needs no App Review, but has more setup than TestFlight.

To debug on the iPhone, enable **Safari → Develop** on the Mac and use **Develop → [your iPhone]** while the phone is connected or paired wirelessly.

## Project structure

```
src/
  entrypoints/
    background.ts        # Reconciles DNR rules, filters reported scripts, updates counters
    collector.content.ts # Top-frame script collector (no page text)
    popup/               # Toolbar popup (React)
    options/             # Full settings page (React)
  lib/
    domain.ts            # URL -> registrable domain (eTLD+1) and script URL normalization
    pageScripts.ts       # Third-party classification and blocked-script filtering
    rules.ts             # DNR rule builder (block, pause, per-script allow)
    settings.ts          # Local settings schema and storage helpers
    stats.ts             # Local most-blocked-script counters
    messaging.ts         # Extension message types and helpers
    time.ts              # Count and relative-time formatting
    useSettings.ts       # React settings subscription hook
    useStats.ts          # React counters subscription hook
  components/            # Shared switch, icon, and script list
public/icon/             # Generated PNG icons
scripts/
  package-safari.sh      # Build + Xcode project generation
  render-icons.mjs       # Regenerates PNGs from icon.svg
tests/e2e/               # Playwright test and local test server
```

## Permissions

- `declarativeNetRequest` — block and allow script requests without reading them.
- `storage` — store the on/off flag, paused sites, script exceptions, and local counters.
- `activeTab` — read the current tab's domain when the popup opens and reload it after a change.
- Host access to `http`/`https` pages — a content script reads script and script-preload URLs in the top frame. This is what powers the per-page script list and the local counters. It does not read page text, form data, cookies, or request bodies.

## Privacy

Everything runs locally. The only persisted data is the global on/off flag, the list of paused domains, the per-script exceptions, and aggregate blocked-script counters, all in `browser.storage.local`. The content script sends script URLs to the extension's own background worker, never to a server. ScriptShredder makes no network requests of its own and has no analytics, telemetry, accounts, or remote configuration.
